Proposed next-stage design focus: split persistent listener service from interruptible listener consumption
- This section is a forward-looking design proposal for the next scheduler stage.
- The "Current direction" and "Current architecture snapshot" sections below still describe the currently landed baseline.
- Problem statement
  - current camera / microphone scheduling still routes listener-adjacent work through short-lived `P2_FUNCTIONAL` leaf tasks
  - when camera-side work finishes one evaluation too early, the runtime can look like the camera listener "disconnected", because there is no persistent scheduler-visible queue that keeps listener-side service alive until the next explicit reseed
  - the next design step should separate "keep listening alive" from "consume one sample and allow interruption"
- Proposed queue split
  - move from 3 physical queues to 4 physical queues
  - `P1_SYSTEM` = `L0 System`
  - new `P2_REALTIME` = `L1 Persistent Listen`
  - current `P2_FUNCTIONAL` semantics become `P3_INTERACTIVE` = `L2 Interruptible Interaction`
  - current `P3_PARTICLE` semantics become `P4_PARTICLE` = `L3 Throughput`
- Two listening modes
  - `L1 persistent listen`
  - seeded once per enabled listener and kept resident by the scheduler
  - may yield each frame, but may not be removed by normal queue cleanup, focus changes, or worker pressure
  - only `StartTask`, `ResetTask`, `ExitTask`, or explicit listener disable may stop it
  - responsibilities: refresh bridge inputs, keep freshness / availability state current, track sample serials, and request `L2` work when a fresh consumable snapshot appears
  - `L2 interruptible listen-consume`
  - short-lived `CameraTask` / `MicrophoneTask` style work
  - consumes one fresh listener snapshot and hands off to `GenerateParticleTask` / `BreezeTask` / batch flow
  - may be interrupted, skipped, or dropped as stale when workers are scarce, because `L1` remains alive upstream
  - must never start or stop the underlying listener
- Key invariants
  - `bridge_io.cpp` remains the only writer of bridge / listener runtime state
  - `L1` service owns scheduler-visible persistence, not device ownership
  - there must never be duplicate resident `L1` service tasks for the same device
  - `L2` tasks should be seeded from sample serial / epoch changes, not only from `all queues empty`
  - clearing `L2/L3/L4` queues must not clear persistent `L1` service unless the operation is `L0` reset / exit / explicit disable
- Scheduler consequences
  - single-thread mode:
  - each tick checks `P1`, then gives one bounded slice to `P2_REALTIME`, then continues the canonical `L2 -> L3` chain
  - `L1` is persistent but not CPU-monopolizing
  - multi-thread mode:
  - one lane may stay eligible for camera `P2_REALTIME`
  - one lane may stay eligible for microphone `P2_REALTIME`
  - general workers continue `L2/L3`
  - if threads are scarce, `L2` should yield first, not `L1`
  - diagnostics should show whether a listener is alive because of persistent `L1` service or only because an `L2` consumer remains queued
- Data model sketch
  - add a queue container for `P2_REALTIME` and renumber / relabel interactive + throughput queues accordingly
  - add per-listener fields such as `service_task_alive`, `last_seen_sample_ms`, `last_seeded_sample_ms`, `last_consumed_sample_ms`, and optional sample serial / epoch counters
  - consider separate task types such as `CAMERA_LISTENER_SERVICE` / `MICROPHONE_LISTENER_SERVICE`, unless a listener-mode flag gives a cleaner migration

Locked timing / residency contract before the next listener refactor pass
- Do not change the current thread scheduling policy again until this timing contract is implemented intentionally.
- Listener task-type split is now a locked requirement, not a preference.
  - there must be two distinct listener task families rather than one listener task with ad-hoc behavior switches
  - the split must stay explicit in type names, diagnostics, queue reporting, and verification output
- Locked listener task-type contract
  - `Long listener task`
    - purpose:
      - keep the sensor alive for the multi-thread runtime
      - absorb startup cost once and keep freshness / availability state hot
      - act as the scheduler-visible long-lived `L1` residency owner
    - residency:
      - multi-thread primary form
      - intended to remain alive on the dedicated camera / microphone side while the runtime stays in multi-thread mode
    - priority:
      - higher listener priority than the short listener
      - scheduler-facing home remains `L1/P2_REALTIME`
      - when the runtime is in multi-thread mode, this is the listener type that should be favored when long-lived residency must be preserved
    - interruption semantics:
      - may yield internally
      - may not be treated as a normal short-lived interactive task
      - only mode collapse, reset, exit, or explicit listener disable should remove it
  - `Short listener task`
    - purpose:
      - single-thread-specialized listener lease
      - hold the sensor open long enough to survive startup and reach usable coordinate-detection state without being externally rescheduled away too early
      - bridge the deterministic single-thread chain into the old `CameraTask -> MicrophoneTask -> ...` interaction phases
    - residency:
      - single-thread primary form
      - may also appear as the constrained fallback form in `2-thread` mode when only one listener may remain long-lived
    - priority:
      - lower listener priority than the long listener, but still above normal `L2` business consumers
      - should still live in the realtime listener layer rather than being demoted into ordinary `L2` work
      - this gives a stable ordering of:
        - `L0 system`
        - `L1 long listener`
        - `L1 short listener`
        - `L2 interactive consumers`
        - `L3 throughput`
    - interruption semantics:
      - external scheduler paths should not evict it during its protected lease window
      - internal early return is still allowed
      - after the protected lease expires, the runtime may decide whether to reseed another short listener or hand ownership back to a different mode-specific listener form
- Short listener mode is now the locked single-thread specialization target.
  - target lease duration: `10s`
  - startup warmup budget: roughly `0s -> 3s`
  - coordinate-detection bringup budget: roughly `3s -> 5s`
  - stable coordinate-detect window begins around `5s`
  - the full `10s` window is the intended residency budget for the short listener once it is seeded
  - external scheduler paths should not interrupt or evict that short listener again during its active `10s` lease
  - internal early return is still allowed if the task proves it has no useful work left or the listener is explicitly disabled / reset / exited
- Long listener mode remains the locked multi-thread target.
  - long listeners stay resident in `L1/P2_REALTIME`
  - they are intended to stay alive on the dedicated multi-thread sensor side rather than being replaced by short lease listeners
  - in `3-thread` mode the intended shape remains:
    - one long camera listener lane
    - one long microphone listener lane
    - one general interaction / throughput lane
  - in `2-thread` mode the locked working assumption is:
    - one long listener
    - one short listener
    - prefer keeping the camera side as the long listener because camera startup is slower and it is the opening event of the whole interaction chain
    - treat microphone as the better candidate for the shorter lease when only one listener may stay long-lived
- Camera-first ordering is now an explicit implementation constraint.
  - prefer camera listener startup before microphone listener startup when both are competing for limited concurrency
  - prefer preserving camera listener residency when only one long listener can remain active
  - rationale: camera startup latency is longer, and camera mouth-open state is the semantic beginning of the event chain
- This timing contract is intentionally approximate except for the short-listener `10s` lease.
  - `3s` startup and `5s` coordinate-ready thresholds are treated as implementation guidance based on current testing, not yet as hard realtime certification thresholds
  - the key locked requirement for the next pass is:
    - single-thread short listener gets a protected `10s` lease
    - multi-thread keeps long listeners alive
    - constrained two-thread mode biases scarce long-lived residency toward camera
    - long-listener and short-listener priority must remain visibly distinct in implementation and diagnostics

Current direction
- Keep the scheduler model framed as latency tolerance rather than business "importance".
- Keep listeners parallel and long-lived while camera / microphone tasks remain crossed business consumers.
- Preserve the directed task-tree interpretation in runtime diagnostics and UI.
- Treat Stage B, the semantic portion of Stage C, and Stage D as landed work.
- Keep Stage D closed as a documentation / diagnostics / alignment stage rather than expanding it into executable parent-task implementation.
- Keep `L1 Realtime` as a scheduler-facing diagnostic domain for now rather than promoting it into a second runtime-owned policy layer.
- Converge multi-thread behavior toward:
  - no `focus`-driven worker scheduling policy
  - retained `camera -> microphone` gate/window semantics for input validity
  - no requirement for `MicrophoneTask` to wait for `P3` drain before queuing a new particle batch
  - `P1/L0` as the only hard global wait / preemption layer

Current architecture snapshot
- Queue / latency mapping
  - `P1_SYSTEM` = `L0 System`
  - `P2_FUNCTIONAL` = `L2 Interactive`
  - `P3_PARTICLE` = `L3 Throughput`
- `L1 Realtime` is represented by listener state, scheduler timing rules, and explicit scheduler snapshot diagnostics rather than standalone queued tasks or runtime-owned executable records.
- Multi-thread dispatch contract
  - `P1/L0` is a runtime-wide override and may be claimed by any active worker before lane-specific `P2` selection
  - dedicated camera / microphone lanes apply only to `P2` task-family filtering
  - non-camera / non-microphone `P2` work plus the `BatchParticleExecutionTask` feeder remain on the general lane
  - `P3` still drains through `BatchParticleExecutionTask` rather than becoming a second direct worker-owned queue family
- Multi-thread input-window contract
  - `camera_focus_locked` / `microphone_focus_locked` should be treated as input-window state in multi-thread mode, not as worker dispatch policy
  - `camera_gate_open` remains the business handoff from mouth-open detection to microphone sampling
  - `MicrophoneTask` may queue new `GenerateParticleTask` / `BreezeTask` while earlier `P3` work is still draining
  - future multi-thread reseed should come from fresh listener snapshots and gate-valid handoff, not only from `all queues empty`
- Directed parent flows now exist in runtime state as explicit semantic records:
  - `HumanBehaviorTask`
  - `ParticleRootTask`
- Current code mapping
  - `CameraTask` behaves as `CameraDetectTask`
  - `MicrophoneTask` behaves as `BlowDetectTask`
  - `GenerateParticleTask` behaves as `ParticleGenerateTask`
  - `BatchParticleExecutionTask` behaves as `ParticleBatchTask`
  - `SingleParticleTask` behaves as `ParticleMoveTask`
  - `ParticleFadeTask` behaves as `ParticleFadeTask`
  - `BreezeTask` is the fallback branch from blow detection
